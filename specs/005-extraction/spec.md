# F5: Structured extraction (spec)

**Status:** Draft (2026-10-25)
**Phase:** 1
**Plan:** [plan.md](plan.md) · **Tasks:** [tasks.md](tasks.md)

## Summary

For invoices, receipts and purchase orders, a vision AI model reads the document and fills in that type's fields (vendor, GSTIN, dates, line items, tax, totals and so on), with a confidence score for each field. The result is checked against the type's schema, stored as the document's first extraction version, and shown on the document's page. This completes Phase 1: an uploaded invoice shows its extracted data in the UI.

## User stories

- **US1:** As a member, I want the key fields of each document filled in automatically, so that I don't type them.
- **US2:** As a member, I want to see how confident the system is about each field, with the uncertain ones highlighted, so that I know what to check.
- **US3:** As a member, I want to see the vendor and total in the document list, so that I can find documents quickly.
- **US4:** As the operator, I want every stored extraction to be valid against a versioned schema and to record how it was produced, so that later reviews, corrections and evals are reliable (ADR-0005).

## Acceptance criteria

- **AC1:** WHEN an invoice, receipt or purchase order reaches the extraction step, THEN its fields are extracted using that type's schema, stored as extraction version 1 with a confidence (0 to 1) for each field, and the document moves to `NEEDS_REVIEW`.
- **AC2:** Schemas exist for invoice, receipt and purchase order (version 1), sharing common definitions for money, party (name, GSTIN, address) and address. Every field is always present; a value missing from the document is `null`. A GSTIN must match the official 15-character format.
- **AC3:** WHEN the AI's answer doesn't match the schema, or the confidences are missing or out of range, THEN nothing is stored for that attempt, the attempt is recorded as an invalid answer, and the step is retried (F3 AC3). After the last attempt the document fails with "Couldn't extract valid data".
- **AC4:** Each stored extraction records the schema it was checked against, the prompt version, the AI call that produced it, and that it came from the model. Extractions are never edited in place; later changes (F6, F7) add new versions.
- **AC5:** Running extraction again for a document that already has a version from the current processing run makes no new AI call and stores nothing new (F3 AC6).
- **AC6:** WHEN a member opens a processed document, THEN they see the extracted fields in a readable layout (including line items as a table), each field's confidence, fields below 0.8 confidence highlighted, and a toggle to see the raw JSON.
- **AC7:** WHEN an extraction becomes the current version, THEN the document's vendor name, document date, total amount and currency are updated from it, and the document list shows vendor and total.
- **AC8:** Money amounts are stored and shown exactly as extracted (no rounding through floating point). The cost and time of processing each document can be computed from the recorded AI calls.

## Edge cases

- **Document in another currency:** currency is extracted as an ISO code; amounts are not converted.
- **No GSTIN on the document** (e.g. a foreign vendor or a small receipt): `null`, not an error.
- **GSTIN-like text that fails the format:** the model must return `null` or a value matching the format; anything else fails schema validation (AC3). The checksum check is F6.
- **Line items spanning pages:** one list; the model sees the whole file.
- **Totals that don't add up:** stored as extracted. Checking arithmetic is F6.
- **Many line items:** no limit beyond the model's output size; an answer cut off by the output limit fails validation and is retried (AC3).

## Non-goals

- Validating arithmetic, GSTIN checksums, duplicates or vendors (F6).
- Editing fields or approving documents (F7).
- Accuracy measurement (F11). Phase 1 shows results; Phase 2 measures them.
- Other providers or fallback (F10).

## Decisions (proposed defaults; approve or change)

- **D1. Model:** `gemini-flash-latest` for extraction, as configuration (confirmed against AI Studio when implementing, as in F4).
- **D2. Low-confidence threshold:** 0.8 for highlighting; configuration, revisited with eval data in Phase 2.
- **D3. Field set:** as listed in plan §4, focused on Indian GST invoices (GSTIN, HSN/SAC, CGST/SGST/IGST) since the evals use SROIE/CORD plus synthetic Indian invoices.
- **D4. Sample documents:** synthetic PDFs generated by a script in `evals/samples/` (no real business data), used for manual checks now and the eval set later.
